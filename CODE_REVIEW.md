## Общая оценка

Кодовая база в хорошей форме — заметно дисциплинированнее, чем обычно бывает у плагинов такого размера. Устаревших API почти нет (нет `nvim_buf_set_option`, `tbl_flatten`, `tbl_islist`; `vim.uv` вместо `vim.loop`), augroup-ы везде с `clear = true`, квотинг централизован в `sql.lua`, комментарии объясняют *почему*, а не *что*, чистые функции экспортированы для тестов. Настоящих подтверждённых багов немного — они перечислены первыми.

Главный долг — **структурный**: отсутствие общего слоя привело к расползанию копий. Центрированный float написан ~5 раз, JSON pretty-print — 3 раза, `project_root()` — 4 раза, определение адаптера по URL — 3 раза (и копии уже разошлись). `view.lua:_setup_keymaps` — одна функция на 3054 строки, `init.lua:setup()` — ~900 строк, включая чужую логику Query Doctor.

## 1. Подтверждённые баги (проверены вручную по коду)

### 1.1 Lua-фоллбэк форматтера ломает операторы PostgreSQL — `format.lua:121-130`
Ветка `->>` (строка 128) недостижима: двухсимвольная проверка `c2 == "->"` (строка 122) срабатывает раньше. Агент прогнал `M._format_lua`: `data ->> 'name'` → `data -> > 'name'`, `a @> b` → `a @ > b`, `tags && ARRAY['a']` → `tags & & ARRAY [ 'a' ]`. Срабатывает у всех без установленного `sql-formatter`/`pg_format`/`sqlfluff` — `gF` молча портит запрос.
**Фикс:** проверку трёхсимвольных (`->>`, `#>>`) поднять выше двухсимвольных; в двухсимвольный список добавить `@>`, `<@`, `&&`, `#>`, `<<`, `>>`.

### 1.2 `run_cmd` бросает исключение при отсутствии CLI-бинаря — `adapters/init.lua:22`
`vim.system` кидает `error()` на ENOENT, а `pcall`-а нет. Заголовки адаптеров обещают «never throw», но проверку `executable()` делают только `query`/`execute`/`ping`. Пример: `schema.lua → db.list_tables → psql` без установленного psql даёт Lua-traceback вместо notify.
**Фикс:** `pcall` вокруг `vim.system` внутри `run_cmd`, возврат `("", tostring(err), 1)` — все вызывающие уже обрабатывают `code ~= 0`.

### 1.3 DuckDB ATTACH не экранирует DSN — `duckdb.lua:51`
`string.format("ATTACH IF NOT EXISTS '%s' AS %s;", a.dsn, a.alias)` — без `:gsub("'", "''")`, хотя валидационный путь того же ATTACH (`duckdb.lua:794`) экранирует. DSN приходит из `:GripAttach` и персистится — одна кавычка ломает все последующие запросы соединения.
**Фикс:** одна строка — привести к виду строки 794.

### 1.4 `vim.cmd("GripExplain " .. sql)` ломается на многострочном SQL — `view.lua:1914`, `view.lua:4642`
`vim.cmd` делит аргумент по переводам строк и выполняет каждую как команду; SQL из query pad многострочный.
**Фикс:** звать `vim.cmd("GripExplain")` без аргумента — `init.lua:1829-1836` сам резолвит SQL из сессии той же логикой.

### 1.5 `ga` агрегирует устаревшее визуальное выделение — `view.lua:4354-4361`
`grid_aggregate` замаплен только в normal mode, но читает `'<`/`'>` — метки *предыдущего* выделения. После любого визуального выделения ранее `ga` тихо агрегирует старый диапазон вместо всей колонки.
**Фикс:** в normal-маппинге всегда брать полный диапазон; для выделения — отдельный visual-маппинг с `get_visual_rows()`.

### 1.6 `DROP TABLE ... CASCADE` — синтаксическая ошибка в SQLite — `ddl.lua:258-260`
Проверено: `sqlite3 ":memory:" "DROP TABLE t CASCADE"` → syntax error. В MySQL слово парсится, но игнорируется (ложное ощущение каскада). Фикс меняет генерируемый SQL — **требует твоего решения**, не «безопасная» правка.

### 1.7 Мелкие подтверждённые дефекты
- `view.lua:5060` — `s.state.total_rows` никогда не задаётся (везде `session.total_rows`), метка `[N rows]` в `gJ` всегда пустая.
- `view.lua:756` — хайлайт-группа `GripColType` нигде не определена, буллет фильтра не подсвечивается.
- `sqlserver.lua:60,153` — `SET NOCOUNT ON` подавляет `(N rows affected)`, который `execute` затем парсит → всегда `affected = 0`.
- `init.lua:885-887` — refresh после DDL обновляет *произвольный* грид (`pairs` + `break`), а не активный.
- `query_pad.lua:125-128` — единственный `vim.schedule` в кодовой базе без проверки `nvim_buf_is_valid`; после wipe пада бросит «Invalid buffer id».
- `ai.lua:274-290` — при `#mentioned > 30` граница цикла отрицательная, лимит в 30 таблиц обходится.

## 2. Производительность

### 2.1 Кубический рендер сетки: `effective_value` — `data.lua:278-279` + `view.lua:473,625,661` ⭐ самый жирный выигрыш
`effective_value` перестраивает карту `col_idx` на **каждый вызов**, а `view.lua` зовёт её трижды на ячейку (ширины, строки, хайлайты). Сетка 100×40 → ~480 000 вставок в таблицу за перерисовку; 1000×20 → ~1.2 млн. Итог `O(rows × cols²) × 3`.
**Фикс (два независимых):** мемоизировать `col_idx` по `state.columns` (комментарий в `data.lua:46-52` фиксирует, что columns не мутируется); в `view.lua` переиспользовать уже вычисленный `display_rows[di][i]` вместо повторных вызовов. Вместе — честный `O(rows × cols)`.

### 2.2 Подсветка колонки перестраивает extmark каждой строки на каждый ход курсора — `view.lua:5178-5225`
`CursorMoved` чистит namespace и ставит ~1001 extmark на страницу в 1000 строк даже при `j`/`k`, когда колонка не изменилась.
**Фикс:** мемо последней подсвеченной колонки на `session._render` (рендер создаёт свежий `_render` → кэш инвалидируется сам) + ранний `return`.

### 2.3 Сэмплирование ширин сведено на нет — `view.lua:469-481`
`calc_col_widths` сэмплирует 100+10 строк, но вызывающий сперва материализует `display_rows` для **всех** строк, а единственный потребитель — сам `calc_col_widths`. На 10 000 строк ~9 890 материализованы впустую.

### 2.4 N+1 спавнов CLI
- `view.lua:1698-1718` (`fetch_view_fk`, клавиша `7`) — запрос на каждую таблицу схемы, хотя `db.get_referencing_foreign_keys` (`db.lua:263`) делает это одним запросом и уже используется в `_fk_referencing`.
- `ddl.lua:242-256` (`drop_table`) — тот же паттерн, тот же готовый API.
- `ai.lua:294-302` — до 90 синхронных спавнов (3 × 30 таблиц), хотя `db.get_schema_batch` реализован у всех пяти адаптеров.
- `sqlite.lua:293` (`get_indexes`) — процесс на индекс; сворачивается в один JOIN через `pragma_index_info`.

### 2.5 Прочее
- `db.lua:73-80` (`parse_csv`) — посимвольная сборка quoted-полей: O(n²) на больших blob-ах + аллокация строки на каждый байт (`raw:sub(i,i)`). Лечится `raw:find('"', i, true)` + `table.concat` и `raw:byte(i)`.
- `completion.lua:472-514` — на каждый ввод символа конкатенация всего буфера + 4 прохода `gmatch`; кэш по `b:changedtick`. Плюс `warm_schema` — no-op для всех, кроме DuckDB (async-вариант есть только там), так что холодный кэш = блокирующий спавн CLI посреди набора. *(warm_schema: снято третьим проходом — см. §9.)*
- `connections.lua:517-545` (`switch`) — 4 чтения + 2 записи одного файла за одно переключение; `history.lua:69-109` — полная перезапись файла истории на каждый запрос (JSONL позволяет append).
- `grip_picker.lua` — `filtered_items()` трижды за рендер; `view.lua:183-189` — per-символьные `vim.fn`-вызовы в `truncate_display`, ASCII fast-path снял бы почти всё.

Первый проход:

- `c2f64da`: `sqlserver://`/`mssql://` перестали определяться как «SQLite» в подсказке `GripFill` и как «SQL» в промпте AI; `mariadb://` в `GripFill` больше не «SQLite», а «MySQL». - `601ac28`: видимое поведение **не** изменилось — разошедшаяся пятая копия карты вкладок оказалась мёртвой (никто не передавал `opts.view` числом), поэтому она удалена, а не примирена.
- `45b3fd9`: вывод JSON в row view и FK-float изменился — это исправление дефекта, детали в теле коммита.

Второй проход:

- `24b379c`: `DROP TABLE ... CASCADE` больше не генерируется для sqlite/mysql/sqlserver — в SQLite это была синтаксическая ошибка, в MySQL слово молча игнорировалось. Взамен диалог подтверждения для этих трёх адаптеров получил предупреждение о том, что зависимые FK каскадом не снимутся.
- `a499cf7`: `execute` у sqlserver возвращает реальное число затронутых строк вместо неизменного 0, а строка `(N rows affected)` попадает в `message` как хвостовой текст.
- `23b74ad`: для postgresql/mysql/duckdb схемо-квалифицированная цель `DROP TABLE` (`public.users`) наконец получает честное определение входящих FK. Раньше скан сравнивал квалифицированное имя с bare-`ref_table`, который возвращают все пять адаптеров, и всегда находил ноль — то есть предупреждение о зависимостях для таких имён не показывалось никогда.
- `ed91063` (правка к `23b74ad`): у той же замены был и непреднамеренный побочный эффект — старый поштучный скан пропускал саму удаляемую таблицу (`if tbl.name ~= table_name`), а `db.get_referencing_foreign_keys` этого не делает ни в одном из четырёх выделенных запросов, ни в generic-фоллбэке. Из-за этого таблица с иерархической колонкой (`parent_id`, `manager_id`) выглядела зависимой: на postgresql/duckdb к `DROP TABLE` молча добавлялся `CASCADE` (а он сносит и зависимые вьюхи, и FK-констрейнты чужих таблиц), на остальных показывалось ложное предупреждение. Само-ссылка теперь отсекается в `M._filter_referencing`; сверено вживую на SQLite-фикстуре — таблица с настоящим входящим FK `CASCADE` по-прежнему получает.
- `ad24958` / `5f195f6`: `get_schema_batch` у duckdb теперь отдаёт настоящий `is_nullable` (был захардкожен `""`), у sqlserver `data_type` несёт длину/точность как в `get_column_info`; две ветки каталога у duckdb сведены в одну на `duckdb_columns()`/`duckdb_views()` с устойчивым порядком колонок. Вживую проверена только duckdb-часть (см. §9); sqlserver-часть — нет, `sqlcmd` в этом окружении не установлен.
- `b02699c`: `omnifunc` читал буфер `0` (sentinel «текущий») — как ключ кэша он склеил бы алиасы всех буферов, поэтому теперь резолвится настоящий `bufnr`. Латентный баг, исправленный попутно.
- `47b3543`: `properties.lua`, `profile.lua`, `diff.lua` выравнивают текст по display-ширине, а не по длине в байтах. Не-ASCII теперь рендерится ровно (раньше байтовый срез по display-числу резал символ пополам и оставлял `<d0>`), ASCII-вывод побайтово тот же — проверено дифференциально, в том числе на 4000 случайных строк в тесте `truncate_display`. Сама пара `truncate_display`/`pad_display` переехала из `view.lua` в `ui.lua` бит-в-бит и получила необязательный параметр `marker` для `"~"`, который уже использовали `properties`/`diff`. `er_diagram.lua` проверен и оставлен как есть: его побайтовый trim самокорректируется, потому что оборванная UTF-8-последовательность рисуется как 4-клеточный `<xx>` и всегда шире символа, который она заменила.

## 10. Четвёртый проход (2026-07-27): полировка и ретроспектива

Мейнтейнер решил не оставлять «мелкие заусенцы» прежнего §10 в документе, а закрыть их перед
слиянием, и отдельно — проверить ретроспективно, верны ли принятые за три прохода решения.

### Задача 22 — полировка (`344a122`..`86002ca`, 9 коммитов, ревью APPROVED / APPROVED_WITH_MINORS)

- Guard-пути `get_schema_batch_async` во **всех пяти** адаптерах доставляют колбэк только через
  `vim.schedule` — колбэк больше не может сработать раньше, чем функция вернёт управление.
  У PostgreSQL guard'а нет и не нужно: его синхронный близнец тоже не отсеивает URL заранее
  (`psql` сам вернёт ненулевой код), паритет соблюдён.
- Появился прямой спек `run_cmd_async` (happy path, ENOENT, watchdog, ровно одна доставка);
  осиротевший раздел тех же тестов переехал к нему из `sqlserver_schema_spec.lua` без потери
  ассертов.
- `ai.lua` не спавнит батч схемы при нуле таблиц; `properties.lua` (`R`/`+`/`T` **и** `D`)
  закрывает флоат детерминированно, а не окольно через `WinLeave`.
- Пункт про `bare()` в `ddl.lua` закрыт **комментарием, а не заменой**: `bare()` и
  `sql.split_table_name` расходятся (трёхчастные имена, кавычки, вырожденные входы), просто ни
  один расходящийся вход недостижим через адаптеры. Ревьюер и имплементер разошлись в фактах о
  вырожденных случаях — спор разрешён исполняемым зондом: `split_table_name(".")` даёт `""`, а
  не `"."` (висячую точку срезает пересборка в `unquote_ident`), `bare()` на всех трёх
  вырожденных входах даёт `nil`. Комментарий приведён к фактам (`86002ca`).

### Ретроспектива решений (`retro-report.md`, отдельный агент, только чтение)

Девять решений трёх проходов перепроверены чтением кода и живыми прогонами: **7 правильных,
2 спорных, 0 неправильных, блокеров до merge — ноль.** Что подтвердилось живьём:

- обёртка `; SELECT ROW_COUNT()` в mysql проверена на ~25 формах SQL (хвостовые `--`/`#`
  комментарии, `CALL` с несколькими result set'ами, пользовательская колонка с именем
  `ROW_COUNT()`) — ни одна не сломалась;
- `-b` у sqlcmd срабатывает на severity ≥ 11 и **не** трогает `PRINT`/warning'и;
- все пять путей доставки `run_cmd_async` дают ровно одну доставку и ноль утёкших таймеров;
- буфер-локальные маппинги после дробления `keymaps_tool.lua` отличаются от `main` ровно на
  два намеренных visual-`ga`, контракт `ctx.view` соблюдён без единого нарушения;
- ветка `\N` в `db.parse_batch` **безопасна конструктивно**, а не «на всякий случай»: `--batch`
  эскейпит обратный слэш, поэтому настоящее значение `\N` приезжает тремя байтами;
- reverse-FK на не-`dbo` схемах SQL Server проверен **позитивно** (`app.parent`/`app.child`) —
  прежняя запись в «не проверено живьём» закрыта;
- ASCII-фастпат `truncate_display` прогнан дифференциально против общего пути: 1800 комбинаций
  (CJK, эмодзи, диакритика, табы), ноль расхождений.

Два «спорных» — не корректность, а качество кода, оба вынесены в §11: срез `%b()` в
`profile.classify_column` и ставший недостижимым фоллбэк reverse-FK. Из её же «мелочей» сразу
закрыта одна: `ui.lua:39` (`ell_w <= width and width <= ell_w` → `ell_w == width`, `db0595b`,
поведение не менялось).

## 11. Что осталось

### Транспортные ограничения CLI-адаптеров (задокументированы, чинить = менять транспорт)

- **MySQL `--batch`**: NULL приходит литералом `"NULL"` и неотличим от строки `'NULL'` (пустая
  строка при этом отличима); пустой результат не печатает даже заголовков (`columns = {}`, PG их
  сохраняет). Оба закреплены характеризационными тестами в `mysql_integration_spec.lua`. Данные
  транспорт при этом **не теряет**: `\t`, `\n`, `\\`, `\0` эскейпятся клиентом и корректно
  разэскейпливаются.
- **PG `psql --csv`**: NULL и `''` оба приходят как `""` (без `\pset null` не различимы).
- **SQL Server `-W -s \t` — единственный по-настоящему лоссовый транспорт из пяти.**
  Подтверждено живьём: значение с `\n` рассыпает строку на две (хвост уезжает в чужую колонку),
  значение с `\t` даёт лишнее поле. Это тихая порча данных в гриде, но `parse_sqlcmd_table`
  побайтово совпадает с `main` — ветка не внесла и не усугубила. Плюс `explain` теряет отступы
  плана, а строка `GO` внутри пользовательского SQL расщепляет батч (деградация тихая, ошибки
  нет). Лечение всего класса — другой транспорт (`FOR JSON PATH`), отдельная задача, и она
  единственная осталась «на пять адаптеров одна».

### Семантика `affected` расходится между адаптерами (поле пока никто не читает)

- sqlserver `execute` парсит **первое** `(N rows affected)`, mysql — `ROW_COUNT()` **последнего**
  стейтмента, sqlite — `changes()` последнего, pg — первый тег. Для батча `BEGIN;…;COMMIT;`
  (`init.lua:355`) mysql даёт гарантированный 0 (последний стейтмент — COMMIT). Все 13 вызовов
  `db.execute()` результат отбрасывают, поле не читает никто. Если `.affected` когда-нибудь
  начнут показывать пользователю, семантику надо сначала выровнять.

### Найдено ретроспективой (после merge, отдельными правками)

- **Недостижимый фоллбэк reverse-FK.** После того как sqlserver получил собственный
  `get_referencing_foreign_keys`, все пять адаптеров реализуют метод: guard в `ddl.lua:53`
  сработать не может, а скан по голому имени в `db.lua:284-304` (N+1 запросов) недостижим.
  ~30 строк мёртвого кода плюс комментарий, описывающий несуществующий путь, — удалить или
  переписать как «задел под шестой адаптер».
- **CI не гоняет интеграционные спеки.** `.github/workflows/test.yml` поднимает только SQLite,
  поэтому 16 mysql-тестов и pg-спеки будут тихо гнить. Гейт по env выбран верно (требовать
  Docker в каждом прогоне нельзя), но нужна отдельная job с `services:`-контейнерами. Skip при
  этом не молчаливый — печатает причину (нет переменной / нет CLI / сервер недостижим).
- **NUL-байт роняет отрисовку ячейки** (`Vim:E976: Using a Blob as a String` через
  `strdisplaywidth`). Воспроизведено сквозным путём на живом MySQL. Не регрессия: и разэскейп
  `\0`, и вызов есть на `main`, а ASCII-фастпат ветки даже сузил зону поражения.
- **`sql.unquote_ident(nil)` возвращает строку `"nil"`** (следствие `tostring(name)`), из-за чего
  mysql-URL без имени БД строит фильтры `table_schema = 'nil'` и тихо отдаёт пустые метаданные.
  Дефект существует и на `main`; наивная однострочная правка рискует уронить `esc(nil)` у
  вызывающих — нужна отдельная задача с проверкой всех семи мест.
- **Асимметрия `stdin`**: `run_cmd` принимает `opts.stdin`, `run_cmd_async` — нет. Сегодня
  безвредно (stdin нужен только sqlserver'у для GO-батчей на блокирующем пути), но закроет
  дорогу асинхронному `explain`.
- **`%b()` в `profile.classify_column`**: на 45 входах расходится с обрезанием по первой `(`
  ровно один раз — и именно там `%b()` ошибается (`enum('a)b','print')` → numeric). Замена — три
  символа, но класс исчезающе мал. Попутно `point` классифицируется как numeric (подстрока
  `int`) — так же и на `main`, ветка эту эвристику строго улучшила.

### Мелкие заусенцы (не блокеры)

- Неиспользуемый параметр `bufnr` в `keymaps_schema.lua`/`keymaps_ai.lua` (плата за единый
  шаблон `M.setup(bufnr, ctx)`); список 17 разрешённых полей `ctx.view` в комментарии не
  проверяется автоматически.
- `history._count_lines` читает файл целиком на каждый `record()` (принятый размен, ≤750 строк).
- Замороженный §6 всё ещё формулирует CASCADE/NOCOUNT как «требующие решения» — указатель на §8
  стоит, сама правка при следующей разморозке §1–6.

- `varbinary(max)` (та же `-1`-ветка, что у `nvarchar(max)`, но живьём не наблюдалась);
  composite FK на живых PG/MySQL (`group_referencing_fks` покрыт parse-тестами sqlserver и
